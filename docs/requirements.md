# LLM API 代理 —— 需求规格

> 状态：已确认（2026-08-27）
> 技术栈：Go，单二进制。

## 背景与问题

本地应用直连第三方大模型 API，遇 429 限流、5xx、超时、连接失败等报错，单点直连导致一次报错就失败、无备用通道。需要一个中间代理：

- 本地应用把请求发给代理；
- 代理负责**重试 + 超出阈值后自动轮询下一个 API/Key**；
- 结果**原封不动**带回，调用方不改任何代码、不改任何内容。

## 核心目标

对外表现成一个「更稳的 API」。

## 一、透明转发（最高优先约束）

- 请求：`path`、`query`、`headers`、`body` **逐字节原样**转发。
- 响应：`status`、`headers`、`body` **原样**返回。
- SSE 流式必须**边收边转**，不能缓冲成整段（`stream=true` 是关键场景）。
- 不改任何内容：包括工具调用、多模态等场景。

## 二、路由与多协议

- 统一一个 base URL，按 **路径路由** 分流：
  - `/v1/chat/completions` 等 → **OpenAI 组**
  - `/v1/messages` 等 → **Anthropic 组**
- 上游配置：每条上游 = `base URL + key + protocol（OpenAI / Anthropic）`。
- 添加时选择协议格式；**轮询/重试只在同协议组内进行**，两种格式永不复用 key。
- 无自定义路径；无路径匹配时按默认组处理。
- **Anthropic 组先搭好结构，主链路优先做 OpenAI**，后续补全 Anthropic 细节验证。

## 三、重试

- **只重试**：429、5xx、超时、连接类错误。
- **直接透传不重试**：400、401、403 等业务性/鉴权错误。
- 重试次数上限可配。
- 间隔用**指数退避 + 抖动**（避免限流后二次集中冲击）。

## 四、轮询

- 某 key 重试超过阈值 → 自动切下一个。
- 切换策略可配（顺序轮询，可扩展随机/跳过故障）。
- 每个上游记录**健康状态**（连续失败数、上次错误时间、最近限流/错误），轮询时优先避开正被限流的 key。

## 五、配置与存储

- 配置文件存上游列表 + 全局策略参数；Web 页面改动时回写文件。
- 本地/内网场景，不用数据库。

## 六、Web 页面（三块）

1. **配置管理**：增删改查上游 API/key、设协议格式、重试次数、轮询策略。
2. **监控与日志**：每次调用记录（时间、上游、key 指纹、status、耗时、错误）、各上游健康状态、实时查看限流/失败。
3. **统计报表**：总调用量、成功率、失败分布、各 key 用量趋势。

## 七、技术栈与部署

- Go 单二进制，本地/内网直接部署。
- 代理入口端口（默认 8080）、管理页面端口（默认 8081），均配置化。
